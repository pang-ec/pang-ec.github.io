표준 백업 정책이 안 통하는 이유
— MVNO 고객사 아키텍처 분석기

2026.08.21 아키텍처

새로 온보딩하는 MVNO 고객사의 AWS 서울 리전 환경에 표준 백업 정책 템플릿을 그대로 적용하려다 막혔다. 템플릿이 전제하는 세 가지가 이 환경엔 없었기 때문이다.

템플릿이 가정하는 것들

  • EKS 워크로드의 PV/PVC 스냅샷
  • 자체 관리형 DB 인스턴스
  • 야간 배치로 도는 증분 백업 스크립트

실제 환경은 달랐다

이 고객사는 EKS를 쓰지 않고, RDS를 관리형으로 운영하며, AWS Backup이 증분 스냅샷을 자동으로 처리하고 있었다. 즉 템플릿이 대응하려던 "직접 관리해야 하는 위험" 자체가 애초에 존재하지 않는 구조였다.

이 부분은 실제 고객사 아키텍처를 요약한 예시 초안입니다. 발행 전 세부 내용과 수치를 다시 확인하고 채워 넣으세요.

팀장님께 어떻게 설명했나

"정책이 없다"가 아니라 "정책이 이미 AWS 관리 영역으로 이관되어 있다"는 관점으로 설명을 바꾸자 훨씬 쉽게 납득이 됐다. 대신 우리가 새로 정의해야 했던 건 AWS Backup 플랜의 보존 주기와, 관리형 서비스 밖에 있는 극소수 리소스에 대한 별도 백업 규칙이었다.

정리

표준 템플릿은 "가장 흔한 패턴"을 가정할 뿐, 모든 환경에 강제로 맞출 대상이 아니다. 중요한 건 템플릿을 지키는 게 아니라 템플릿이 방어하려던 위험이 이 환경에도 실제로 존재하는지를 먼저 확인하는 것.
