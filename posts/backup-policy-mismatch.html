표준 백업 정책이 통하지 않았던 이유
— 고객사 아키텍처 분석

2026.08.21 아키텍처

새로 온보딩하는 고객사의 AWS 서울 리전 환경에 팀에서 쓰던 표준 백업 정책 템플릿을 그대로 적용하려다 막혔다. 템플릿은 특정 세 가지 조건을 전제로 만들어져 있었는데, 이 환경엔 그 조건이 하나도 맞지 않았다.

템플릿이 가정하는 환경

기존 표준 백업 정책 템플릿은 다음 세 가지가 존재한다는 걸 전제로 설계돼 있었다.

  • EKS 워크로드가 쓰는 PV/PVC — 별도 스냅샷 정책이 필요
  • 자체 관리형(Self-managed) DB 인스턴스 — EC2 위에서 직접 백업 스크립트를 돌려야 함
  • 야간 배치로 도는 증분 백업 스크립트 — cron 기반 자체 구현

실제 환경과의 차이

이 고객사는 EKS 자체를 쓰지 않았고, DB는 RDS 관리형으로 운영 중이었으며, 증분 스냅샷은 AWS Backup이 자동으로 처리하고 있었다. 즉 템플릿이 방어하려던 "직접 관리해야 하는 백업 위험" 자체가 이 환경에는 애초에 존재하지 않았다.

팀장님께 어떻게 설명했나

"정책이 없다"가 아니라 "정책이 이미 AWS 관리 영역으로 이관되어 있다"는 관점으로 설명을 바꾸자 훨씬 쉽게 납득이 됐다. 대신 우리가 새로 정의해야 했던 건 AWS Backup 플랜의 보존 주기와, 관리형 서비스 밖에 있는 극소수 리소스에 대한 별도 백업 규칙이었다.

새로 정의한 AWS Backup 플랜

기존 템플릿의 cron 스크립트 대신, AWS Backup 플랜 규칙으로 보존 주기를 다시 정의했다. 구조를 단순화한 예시는 아래와 같다.

{
  "BackupPlanName": "customer-managed-baseline",
  "Rules": [
    {
      "RuleName": "daily-short-term",
      "TargetBackupVaultName": "customer-vault",
      "ScheduleExpression": "cron(0 18 * * ? *)",
      "Lifecycle": { "DeleteAfterDays": 14 }
    },
    {
      "RuleName": "weekly-long-term",
      "TargetBackupVaultName": "customer-vault",
      "ScheduleExpression": "cron(0 19 ? * SUN *)",
      "Lifecycle": {
        "MoveToColdStorageAfterDays": 30,
        "DeleteAfterDays": 365
      }
    }
  ]
}

일간 규칙은 RDS 자동 스냅샷과 별개로 짧은 보존 주기(14일)만 담당하게 하고, 장기 보존이 필요한 항목은 주간 규칙으로 분리해 콜드 스토리지로 이관되도록 했다. RDS 자체 스냅샷과 중복되지 않도록 태그 기반으로 대상을 나눈 것이 핵심이다.

대신 새로 정의한 것

템플릿을 버리는 대신, 이 환경에 맞게 세 가지를 다시 정의했다.

  1. AWS Backup 플랜 보존 주기 — RDS 자동 스냅샷과 별개로, 장기 보존(월간/연간)이 필요한 항목만 별도 플랜으로 분리
  2. 관리형 서비스 밖 리소스 백업 — EC2 애플리케이션 서버 등 소수의 비관리형 리소스에 한해 개별 백업 규칙 적용
  3. 복구 시나리오 문서화 — "장애 시 무엇을 어디서 복구하는지"를 관리형/비관리형으로 나눠 MSP 핸드오버 문서에 명시

정리

표준 템플릿은 "가장 흔한 패턴"을 가정할 뿐, 모든 환경에 강제로 맞출 대상이 아니다. 중요한 건 템플릿을 지키는 게 아니라 템플릿이 방어하려던 위험이 이 환경에도 실제로 존재하는지를 먼저 확인하는 것. 이번 건으로 다음 온보딩부터는 "표준 템플릿 체크리스트"보다 "이 환경에서 관리형/비관리형 경계가 어디인지"부터 먼저 그려보는 순서로 바꿨다.
