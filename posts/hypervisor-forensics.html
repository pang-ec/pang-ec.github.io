원인 불명 재부팅 장애
— 리눅스 로그로 하이퍼바이저 개입을 추적하다

2026.07.30 트러블슈팅

KT Cloud 위에서 운영 중인 DB 서버가 예고 없이 재부팅됐다. 문제는 OS 레벨에서 종료 명령이 실행된 흔적이 전혀 없었다는 것. 로그를 하나씩 걷어내며 원인을 좁혀간 과정을 정리한다.

재부팅 시각부터 특정

가장 먼저 한 건 정확한 재부팅 시각을 확인하는 것이었다.

last -x reboot | head -5
uptime -s

last -x reboot로 최근 부팅 이력을, uptime -s로 현재 부팅 이후 시작 시각을 확인해 두 값을 대조했다. 이 시각을 기준으로 이후 로그를 전부 역추적했다.

OS 레벨 종료 흔적 확인

정상적인 shutdown이나 reboot 명령이 실행됐다면 로그에 남는다. 세 군데를 순서대로 확인했다.

1. /var/log/secure — 명령 실행 이력

grep -iE "shutdown|reboot|poweroff" /var/log/secure*

사용자가 직접 실행한 종료/재시작 명령이 있었다면 여기 남는다. 결과는 매치 없음(no match) — 즉 누군가 로그인해서 명령을 실행한 흔적이 없었다.

2. /var/log/messages — 종료 시퀀스

grep -iE "shutting down|watchdog|kernel panic" /var/log/messages*
tail -n 100 /var/log/messages

정상 종료라면 서비스가 순차적으로 내려가는 시퀀스가 로그에 남아야 하는데, 로그가 특정 시점에서 뚝 끊겨 있었다. 이 끊김 시점이 앞서 확인한 재부팅 시각과 정확히 일치했다.

3. journald — 부팅 목록으로 경계 확인

journalctl --list-boots
journalctl -b -1 -n 50   # 직전 부팅의 마지막 로그 50줄

다만 이 서버는 journald가 volatile 모드(메모리 저장)로 설정돼 있어서, 재부팅과 함께 이전 부팅의 로그 상당 부분이 유실된 상태였다. 남아있는 일부 로그에서도 종료 관련 유닛 정지 메시지는 확인되지 않았다.

이후 이 서버는 journald를 persistent 모드(Storage=persistent, /etc/systemd/journald.conf)로 바꿔 재부팅 이후에도 로그가 디스크에 남도록 설정을 변경했다. 같은 상황이 다시 오면 이번처럼 증거가 비어있는 일은 없을 것이다.

결론: OS가 아니라 그 아래를 봐야 한다

OS 레벨 원인이 전부 배제되고 나면 남는 건 하이퍼바이저 레벨의 개입뿐이다. 이 지점부터는 우리 쪽 로그만으로는 더 파고들 수 없어서, KT Cloud에 특정 시각의 하이퍼바이저 이벤트 로그와 인스턴스 이벤트 로그를 요청하는 티켓을 작성했다.

티켓에 넣은 핵심 요청 사항

  1. 재부팅 발생 시각 전후 하이퍼바이저 이벤트 로그
  2. 해당 인스턴스에 대한 플랫폼 측 마이그레이션/헬스체크 이력
  3. 동일 호스트의 다른 인스턴스에 동시간대 이상 여부

인프라 엔지니어 입장에서 "우리 쪽엔 원인이 없다"를 증명하는 것도 결국 로그로 하나씩 가능성을 소거해나가는 작업이라는 걸 다시 확인한 사례였다.

조사 순서를 정리하면

비슷한 상황을 또 만났을 때 헤매지 않도록, 이번에 밟은 순서를 체크리스트로 남겨둔다.

  1. 재부팅 시각을 최대한 정확히 특정 (last -x reboot, uptime -s)
  2. OS 레벨 종료 명령 실행 흔적 확인 (secure → messages → journald 순으로)
  3. OS 레벨에서 아무 흔적이 없으면 하드웨어/플랫폼 이슈로 가정 전환
  4. 플랫폼사에 특정 시각 기준으로 좁혀서 로그 요청 (범위가 넓으면 응답이 늦어짐)
