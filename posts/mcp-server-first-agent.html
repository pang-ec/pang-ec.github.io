Claude API로 사내 자동화 만들기
— MCP Server 첫걸음

2026.07.12 AI 에이전트

고객 문의 자동화 AI Agent를 사내 챌린지에 제출하면서 부딪혔던 문제들을 정리한다. 구성은 단순했다: Flask 서버 두 대(5000/5001 포트), NCP VPC API로 ACG 자동화, Gmail SMTP, MS Teams Power Automate 웹훅, Confluence REST API.

겪었던 문제들

  • NCP ACG 규칙을 중복으로 생성하려던 문제 — 생성 전 기존 규칙 조회 로직 추가로 해결
  • 특수문자가 섞인 응답에서 JSON 파싱이 깨지던 문제
  • Teams Adaptive Card 포맷을 안 맞추면 웹훅이 조용히 실패하던 문제
  • 웹훅 방식과 폴링 방식 중 어떤 걸 아키텍처로 선택할지에 대한 고민
이 글은 초안입니다. 실제 코드 스니펫이나 아키텍처 다이어그램을 추가하면 훨씬 읽을 만한 글이 됩니다.

데모 이후

데모가 끝난 뒤 인트라넷 통합은 개발팀이 이어받았고, 나는 비즈니스 프로세스 정의 쪽으로 역할을 옮겼다. 이 과정에서 얻은 제일 큰 교훈은, MSP 엔지니어가 짤 수 있는 자동화의 범위가 생각보다 넓다는 것. 인프라를 다루는 사람이 API까지 직접 엮을 수 있으면 자동화 후보 자체가 훨씬 많아진다.

아키텍처 결정: 웹훅 vs 폴링

초기엔 Confluence/Teams 쪽 변경을 폴링으로 감지하려 했는데, 두 가지 이유로 웹훅으로 바꿨다.

  • 폴링 주기를 짧게 잡으면 API 호출량이 금방 쌓이고, 길게 잡으면 반응이 느려짐
  • Teams는 Power Automate로 이벤트 발생 시점에 바로 웹훅을 쏴줄 수 있어서 실시간성이 훨씬 좋음

다만 웹훅 방식은 수신 서버가 항상 떠있어야 한다는 전제가 붙는다. 그래서 Flask 서버를 NCP 퍼블릭 클라우드에 상시 기동해두는 구조로 갔다.

ACG 중복 규칙, 어떻게 잡았나

같은 포트/대역에 대한 ACG 규칙을 매번 새로 생성하려던 문제가 있었다. NCP VPC API로 생성 전에 기존 규칙 목록을 먼저 조회해서, 동일한 protocol/port/cidr 조합이 있으면 생성을 건너뛰도록 가드를 추가했다. 별거 아닌 로직이지만, 이게 없으면 ACG 규칙이 며칠 만에 수십 개로 불어난다.

이 프로젝트 이후 NCP 리소스를 Claude에서 직접 제어하는 MCP Server(ncp-mcp-server)로 작업을 이어가고 있다. 관련 내용은 별도 글로 정리할 예정.
