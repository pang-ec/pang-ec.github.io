3중화 구성 전환 후 트래픽 검증
— WAF 로그 분석

2026.08.10 성능 분석

대학 고객사의 수강신청 이벤트를 앞두고, 로드밸런서를 새로 3중화 구성으로 바꿨다. 이벤트 당일 실제로 버텨줄지 확인하려고 NCP WAF와 로드밸런서 트래픽 로그를 미리 뜯어봤다.

확인하고 싶었던 것

  • 동시 접속이 몰리는 구간에서 각 인스턴스로 트래픽이 고르게 분산되는지
  • WAF 룰에 걸려 정상 요청이 차단되는 경우가 있는지
  • 응답 지연이나 5xx 에러가 특정 시간대에 몰리는지

구성 변경 개요

CSV 로그를 시간대별로 쪼개서 보기

수강신청 오픈 시각을 기준으로 전후 구간을 나눠 트래픽 볼륨과 에러율을 비교했다. pandas로 시간대별 요청 수와 인스턴스별 분산 비율, 5xx 응답 비율을 뽑아내는 방식으로 접근했다.

import pandas as pd

df = pd.read_csv("waf_traffic.csv", parse_dates=["timestamp"])
df["minute"] = df["timestamp"].dt.floor("1min")

# 분당 요청 수 및 인스턴스별 분산 비율
per_minute = df.groupby(["minute", "instance_id"]).size().unstack(fill_value=0)
distribution_ratio = per_minute.div(per_minute.sum(axis=1), axis=0)

# 5xx 에러 비율
error_rate = df.groupby("minute").apply(
    lambda g: (g["status_code"] >= 500).mean()
)

오픈 직후 몇 분간 요청이 집중되는 패턴은 예상대로였는데, 그 구간에서도 3개 인스턴스의 요청 분산 비율이 크게 어긋나지 않았다는 게 핵심 확인 사항이었다.

표의 수치는 분산 검증 방식을 보여주기 위한 예시 값이며, 실제 리포트에는 고객사 데이터 기준의 정확한 수치와 WAF 차단 로그를 함께 표로 정리해 전달했다.

고객 보고용과 내부 튜닝용을 분리한 이유

같은 데이터를 봐도 고객사에는 "모니터링된 구간 동안 성능 이슈 없음"이라는 결론만 필요했고, 내부적으로는 특정 WAF 룰의 민감도를 낮출지 말지 같은 튜닝 논의가 별도로 있었다. 두 결론을 하나의 보고서에 섞으면 고객 입장에서 불필요한 불안을 줄 수 있어서, 처음부터 결론 문서와 내부 관찰 노트를 나눠서 작성했다.

정리

이벤트성 트래픽 대응에서 제일 중요한 건 "이벤트 당일 대응"이 아니라 "이벤트 전에 구성 변경이 실제로 의도한 대로 동작하는지 데이터로 미리 확인하는 것"이라는 걸 다시 느꼈다. 문제가 생기고 나서 로그를 보는 것과, 문제가 없다는 걸 미리 로그로 증명해두는 것은 완전히 다른 작업이다.
